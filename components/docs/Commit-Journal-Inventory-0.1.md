# Commit Journal Inventory 0.1

**Version:** 0.1
**Date:** 2026-07-27
**Project:** Lunar Linux Website 3.3
**Phase:** Componentization Phase 2 — Step 3
**Status:** Accepted inventory evidence; implementation outcome recorded

## 1. Purpose

This document records the two existing commit-journal renderers and the boundary that may justify a shared component.

The comparison covers:

- the current Moonbase commit journal generated inside `tools/build-site.sh`;
- the archived commit journal generated by `tools/build-archive-index.sh`.

The purpose is not to generalize tables. It is to determine whether the repeated commit presentation is stable enough to extract.

## 2. Current implementations

### 2.1 Current Moonbase Commit Journal

**Producer and renderer:** `tools/build-site.sh`, function `prepare_moonbase_values()`
**Input:** `docs/data/moonbase-news.json`
**Generated intermediate:** temporary `moonbase_commits_file`
**Consumer:** active website page rendering

Root structure:

```html
<div class="moonbase-journal">
  <table class="moonbase-table">
```

Columns:

```text
Commit
Repository
Module
Comment
```

Visible row fields:

```text
commit hash
repository
module
summary
```

Link behavior:

```text
https://github.com/lunar-linux/moonbase-<repository>/commit/<commit>
target="_blank"
rel="noopener"
```

Current renderer responsibilities:

- parse the JSON-line data;
- select only records whose category is `Moonbase`;
- decode supported JSON escapes;
- derive `module` from `title` when absent;
- build the GitHub commit URL;
- escape text and attributes;
- render the table;
- render the current empty state.

The renderer preserves the input order supplied by `moonbase-news.json`.

### 2.2 Archived Commit Journal

**Producer and renderer:** `tools/build-archive-index.sh`, function `build_commits_fragment()`
**Input:** preserved archive JSON or compressed JSON
**Generated fragment:** `cache/archive-commits.html`
**Consumers:** archive pages through `{{ archive_commits_html }}`

Root structure:

```html
<div class="moonbase-journal archive-journal">
  <table class="moonbase-table archive-commits-table">
```

Columns:

```text
Commit
Repository
Module
Comment
```

Visible row fields:

```text
commit hash
repository
module
summary
```

Link behavior:

```text
https://github.com/lunar-linux/moonbase-<repository>/commit/<commit>
target="_blank"
rel="noopener"
title="<date>"
```

Archive producer responsibilities:

- discover archive data files;
- read compressed or plain archive objects;
- parse archived JSON objects;
- validate required fields;
- derive summary and module fallbacks;
- reject unsupported tab characters;
- sort records newest first;
- build the GitHub commit URL;
- escape values;
- render the archive table;
- report archive problems.

## 3. Shared semantic structure

Both implementations render the same four-column commit record:

```text
commit
repository
module
summary
```

Both use the same semantic classes:

```text
moonbase-journal
moonbase-table
commit-id
repository-name
module-name
commit-comment
```

Both use the same GitHub destination rule:

```text
moonbase-<repository>/commit/<commit>
```

Both produce links with:

```html
target="_blank" rel="noopener"
```

This is a proven repeated presentation responsibility.

## 4. Important differences

### Current journal

```text
root classes: moonbase-journal
table classes: moonbase-table
colgroup: present
header: expanded multiline markup
row: expanded multiline markup
link title: absent
empty state: paragraph after table
record order: input order
```

### Archive journal

```text
root classes: moonbase-journal archive-journal
table classes: moonbase-table archive-commits-table
colgroup: absent
header: compact one-line markup
row: compact one-line markup
link title: archive date
empty state: table row
record order: explicitly sorted newest first
```

These differences are currently visible output contracts and should be preserved during first extraction.

## 5. Current duplication

The duplicated responsibilities are:

- journal wrapper;
- four-column table;
- column labels;
- commit-link construction;
- external-link attributes;
- commit, repository, module and comment cells;
- HTML escaping;
- empty-state rendering.

The non-duplicated responsibilities are:

- current JSON-line parsing;
- category filtering;
- JSON escape decoding;
- archive file discovery;
- compressed archive reading;
- archive validation and reporting;
- fallback derivation;
- sorting policy.

## 6. Candidate component boundary

The justified candidate is:

```text
Commit Journal
```

Proposed responsibility:

> Render an already selected and ordered stream of prepared commit records into the established Moonbase commit-journal HTML.

The component may own:

- wrapper and table markup;
- variant classes;
- column headers;
- row markup;
- GitHub commit URL construction from prepared repository and commit values;
- text and attribute escaping;
- external-link attributes;
- optional link title;
- variant empty state;
- preservation of input order.

The component must not own:

- JSON parsing;
- archive discovery;
- decompression;
- category filtering;
- module or summary fallback policy;
- date validation;
- sorting;
- archive reporting;
- statistics generation.

## 7. Candidate input format

A prepared tab-separated file is suitable because all five relevant values are scalar text fields.

Candidate fields:

```text
commit<TAB>repository<TAB>module<TAB>summary<TAB>link_title
```

`link_title` is:

- empty for the current variant;
- the preserved archive date for the archive variant.

However, the current general News Journal contract rejects empty fields. Commit Journal has a legitimate optional field. Its own contract must therefore define field-level requirements rather than copying News Journal validation unchanged.

The producer must reject or normalize embedded tab characters before invoking the component.

## 8. Candidate variants

Only two variants are proven:

```text
current
archive
```

### `current`

- root class: `moonbase-journal`;
- table class: `moonbase-table`;
- current colgroup retained;
- no commit-link title;
- current empty-state paragraph retained;
- expanded current markup retained initially.

### `archive`

- root classes: `moonbase-journal archive-journal`;
- table classes: `moonbase-table archive-commits-table`;
- no colgroup;
- commit-link title supplied from archived date;
- archive empty-state row retained;
- compact archive markup retained initially.

An arbitrary class or arbitrary column interface is not justified.

## 9. Ordering

The component must preserve input order.

Ordering remains producer-owned:

```text
current producer
→ order already present in moonbase-news.json

archive producer
→ sort -r before component invocation
```

This separation avoids hidden policy in presentation.

## 10. URL semantics

Both implementations currently derive the URL as:

```text
https://github.com/lunar-linux/moonbase-<repository>/commit/<commit>
```

This rule is presentation-adjacent but also Lunar-specific.

For Contract 0.1, there are two viable designs:

```text
A. producer supplies complete href
B. component derives href from repository and commit
```

The recommended first design is **B**, because:

- both existing renderers use exactly the same rule;
- it reduces duplicate URL construction;
- the component is explicitly a Lunar Moonbase Commit Journal, not a generic Git table;
- it keeps the prepared record compact.

If provider independence becomes necessary later, the contract can evolve to a prepared `href`.

## 11. Empty states

The two existing empty states differ:

Current:

```html
<p>No Moonbase commits were found for the selected period.</p>
```

Archive:

```html
<tr>
  <td colspan="4" class="commit-comment">No archived commits were found.</td>
</tr>
```

The first extraction should preserve both exactly. Empty-state normalization is a separate decision.

## 12. Date semantics

The date is not a visible column.

In the archive journal it is used only as the commit link's `title` attribute.

In the current journal it is not included in the row markup.

Therefore:

- the component should accept an optional prepared `link_title`;
- it should not invent or parse dates;
- it should omit the `title` attribute when the field is empty.

## 13. CSS ownership

The existing CSS already expresses the shared presentation:

```text
moonbase-journal
moonbase-table
archive-journal
archive-commits-table
moonbase-col-commit
moonbase-col-repository
moonbase-col-module
moonbase-col-comment
commit-id
repository-name
module-name
commit-comment
```

No CSS redesign is required.

The current colgroup classes remain current-variant behavior until a separate CSS review proves they are unnecessary.

## 14. Recommended extraction path

```text
1. Define Commit Journal Contract 0.1-draft
2. Implement components/commit-journal.sh
3. Add direct fixtures for current and archive variants
4. Integrate only the current renderer in build-site.sh
5. Compare the generated active fragment or affected page output
6. Integrate the archive renderer in build-archive-index.sh
7. Compare cache/archive-commits.html byte-for-byte
8. Run the full build
9. Confirm unrelated page signatures remain unchanged
```

Because the current fragment is temporary, validation must preserve the old rendered page or capture the old temporary fragment through a controlled test fixture before replacing the inline renderer.

## 15. Risks

Primary risks:

- changing record order;
- changing multiline versus compact HTML;
- losing the archive date title;
- adding an empty title attribute to current links;
- altering URL escaping;
- moving JSON parsing into the component;
- moving archive validation into the component;
- treating Commit Journal as a generic table renderer;
- broad page signature changes caused only by whitespace.

## 16. Inventory conclusion

A shared Commit Journal component is justified.

The correct boundary is:

```text
prepared ordered commit records
→ Commit Journal renderer
→ HTML fragment
```

The component should remain Lunar Moonbase-specific in Contract 0.1. A generic table component is not justified by the current evidence.


## Implementation outcome

The candidate boundary documented by this inventory was implemented as:

```text
components/commit-journal.sh
```

Its current and archive variants were integrated one producer at a time. Direct
fixture tests passed and generated output remained byte-identical.

This inventory remains evidence of the implementation state observed before
extraction. Historical differences and risks are intentionally preserved.
